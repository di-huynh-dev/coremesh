<Lead>A project I worked on had five product teams shipping into one Next.js app. Every release rode a shared deploy train, and a failing test in search could block checkout's hotfix. We split it into micro-frontends. Six months later every team could deploy on its own — and the bundle had three copies of the same date library, two slightly different button styles, and one production incident caused by a React version mismatch between the shell and a remote. This post is what I'd tell a team before making that move.</Lead>

## They solve an organizational problem

Micro-frontends split a frontend into pieces owned and deployed by different teams, composed into one product. Strip away the tooling and the value is about **people**:

- **Independent deploys.** Team A ships at 10am without waiting for team B's flaky tests.
- **Clear ownership.** One team owns checkout end to end: code, pipeline, on-call, metrics.
- **Incremental migration.** You can replace a legacy app route by route (the strangler pattern) instead of a big-bang rewrite.

Performance and code quality aren't on that list. Micro-frontends don't make code better; they make **boundaries** harder to cross, which helps when the boundaries are right and hurts when they're wrong.

The test I use: is the pain caused by **coordination between teams**, or by the code itself? If three engineers are stepping on each other, you need better modules, not separate deployments.

## What they actually cost

| Cost | What it looks like in practice |
| --- | --- |
| Duplicated dependencies | Without sharing, each app bundles its own copy; with sharing, you get version coupling |
| Inconsistent UX | Spacing, loading states, error messages, focus behavior differ between parts of one product |
| Performance | More JavaScript, more requests, waterfalls when the shell must load before remotes can start |
| Shared state | Auth, cart, feature flags, locale: every app needs them, nobody should own a global store |
| Versioning | A remote ships a breaking change and the shell breaks in production without changing a line |
| Operations | N pipelines, N preview environments, N dashboards, and a way to know which versions are live together |

Teams underestimate the last row. In a monolith, "what's in production" is a commit hash. With micro-frontends, it's a combination of versions **nobody tested together** unless you make it so.

<Callout>
  Micro-frontends move complexity from the codebase into the runtime and the organization. If you don't have a platform team (or at least someone) owning the shell, the shared dependencies and the contracts, that complexity lands on whoever is on call.
</Callout>

## Integration options

There are five main ways to compose apps, differing mostly in **when** composition happens.

| Approach | Composition time | Independent deploy | Isolation | Main risk |
| --- | --- | --- | --- | --- |
| Build-time packages | Build of the host | No (host must rebuild) | None | It's a monorepo with extra steps |
| Module Federation | Runtime, in the browser | Yes | Low (shared JS realm) | Shared dependency versions |
| Import maps + ES modules | Runtime, in the browser | Yes | Low | Tooling, browser support for advanced cases |
| Iframes | Runtime, separate documents | Yes | Strong | UX, accessibility, performance |
| Server-side / route composition | Server or edge | Yes | Per route or fragment | Cross-app navigation and shared layout |

### Build-time packages

Each team publishes a package; the host bundles them. Simple, type-safe, naturally deduplicated — but every change still needs a host rebuild and deploy, so you lose the main reason for micro-frontends. I treat this as a way to organize a monolith.

### Module Federation 2.0

Module Federation started as a webpack 5 feature. Version 2.0, stable since April 2026, decouples the runtime from the bundler and works with Rspack, webpack and others via plugins. It adds a manifest (`mf-manifest.json`) describing what a remote exposes, generated TypeScript types for remotes, runtime plugins, and Chrome devtools showing which remote and shared versions actually loaded.

A remote built with Rsbuild exposes a page and declares what it shares. The checkout team's `rsbuild.config.ts`:

```ts
import { defineConfig } from "@rsbuild/core";
import { pluginReact } from "@rsbuild/plugin-react";
import { pluginModuleFederation } from "@module-federation/rsbuild-plugin";

export default defineConfig({
  plugins: [
    pluginReact(),
    pluginModuleFederation({
      name: "checkout",
      exposes: {
        "./CheckoutPage": "./src/CheckoutPage.tsx",
      },
      shared: {
        react: { singleton: true, requiredVersion: "^19.0.0" },
        "react-dom": { singleton: true, requiredVersion: "^19.0.0" },
        "@shop/design-system": { singleton: true, requiredVersion: "^4.0.0" },
      },
    }),
  ],
});
```

The shell uses the same plugin and `shared` block, but registers remotes at runtime from a config endpoint instead of hardcoding URLs. That's what gives you independent deploys and instant rollbacks: point the config at the previous manifest and you're done. `CheckoutUnavailable` and `PageSkeleton` below are ordinary local components in the shell.

```tsx
import { lazy, Suspense, type ComponentType } from "react";
import { ErrorBoundary } from "react-error-boundary";
import { loadRemote, registerRemotes } from "@module-federation/enhanced/runtime";

type RemoteEntries = Record<string, string>;

export async function registerRemotesFromConfig() {
  const response = await fetch("/api/frontend-remotes");
  const entries: RemoteEntries = await response.json();
  registerRemotes(Object.entries(entries).map(([name, entry]) => ({ name, entry })));
}

const CheckoutPage = lazy(async () => {
  const remoteModule = await loadRemote<{ default: ComponentType }>("checkout/CheckoutPage");
  if (!remoteModule) throw new Error("checkout/CheckoutPage failed to load");
  return remoteModule;
});

export function CheckoutRoute() {
  return (
    <ErrorBoundary fallback={<CheckoutUnavailable />}>
      <Suspense fallback={<PageSkeleton />}>
        <CheckoutPage />
      </Suspense>
    </ErrorBoundary>
  );
}
```

Two things matter more than the config. First, `singleton` doesn't guarantee one version: if versions differ, the highest wins and the others get a console warning. That's exactly how we ended up running a React minor that one remote had never been tested against. Treat shared singletons as a platform-wide contract and upgrade them together. Second, every remote is a network dependency: wrap it in an error boundary with a useful fallback, not a blank page.

One Next.js-specific note: the Module Federation team has announced end of life for `nextjs-mf`, and it never supported the App Router. On Next.js 16, I use route-level composition instead (below).

### Import maps

Native ES modules plus an import map give runtime composition without a federation runtime. The shell's HTML maps bare specifiers to URLs; each team updates its own entry:

```html
<script type="importmap">
  {
    "imports": {
      "react": "/shared/react-19.2.0.js",
      "react-dom/client": "/shared/react-dom-client-19.2.0.js",
      "@shop/checkout": "https://checkout.example.com/releases/412/entry.js"
    }
  }
</script>
<script type="module">
  import { mount } from "@shop/checkout";
  mount(document.getElementById("checkout-root"));
</script>
```

A single import map works in all modern browsers; multiple import maps aren't enabled by default in Firefox yet, so I generate one map per request on the server. The catch: every shared library needs a proper ES module build, and there's no version negotiation like Module Federation's.

### Iframes and server-side composition

**Iframes** give true isolation: separate JS realm and CSS, and a crash stays inside. Good for embedding third-party or legacy tools. For core flows they hurt: focus, sizing, deep links, the back button and screen readers all need extra work, and every frame loads its own framework.

**Server-side composition** splits by route. With Next.js multi-zones, each zone is a normal Next.js app with its own `assetPrefix`, and the main app routes paths to it with rewrites. This is what I recommend most often, because each route still gets full SSR and React Server Components. The main app's `next.config.ts`:

```ts
import type { NextConfig } from "next";

const checkoutOrigin = process.env.CHECKOUT_ORIGIN ?? "http://localhost:3002";

const nextConfig: NextConfig = {
  async rewrites() {
    return [
      { source: "/checkout", destination: `${checkoutOrigin}/checkout` },
      { source: "/checkout/:path+", destination: `${checkoutOrigin}/checkout/:path+` },
      { source: "/checkout-static/:path+", destination: `${checkoutOrigin}/checkout-static/:path+` },
    ];
  },
};

export default nextConfig;
```

The trade-offs: navigation between zones is a full page load, so links across zones must be plain `a` tags, not the `Link` component, and Server Actions need the user-facing domain in `serverActions.allowedOrigins`. If users move between areas constantly, the hard navigations show.

## Design system and routing ownership

The most effective thing for UX consistency is a **shared design system owned by one team**. Tokens as CSS variables (see [design tokens and theming](/blog/design-tokens-and-theming)) are the safest layer to share because they're framework-agnostic and can change at runtime. Components are harder: as a federated singleton, every app must work with the version the shell loads; bundled per app, they drift. I pick singleton and treat a major bump as a coordinated release.

Routing needs equally clear rules:

- The **shell owns top-level routes** and the layout: header, navigation, auth gate.
- Each app owns **everything under its prefix** (`/checkout/*`) and its internal routing.
- Cross-app navigation goes through the URL, never by importing another app's router.

## Contracts between apps

The less apps share, the better. The URL is the best shared state: serializable, linkable, owned by nobody. For the few things apps must tell each other, I publish a small typed event contract:

```ts
export type ShellEvents = {
  "cart:item-added": { sku: string; quantity: number };
  "auth:session-changed": { userId: string | null };
};

export function emitShellEvent<K extends keyof ShellEvents>(type: K, detail: ShellEvents[K]) {
  window.dispatchEvent(new CustomEvent(type, { detail }));
}

export function onShellEvent<K extends keyof ShellEvents>(
  type: K,
  handler: (detail: ShellEvents[K]) => void,
): () => void {
  const listener = (event: Event) => handler((event as CustomEvent<ShellEvents[K]>).detail);
  window.addEventListener(type, listener);
  return () => window.removeEventListener(type, listener);
}
```

The rules matter more than the code: payload changes are **additive only**, a breaking change gets a new event name, and auth stays with the shell — apps ask the shell, they don't read each other's storage. Avoid a global shared store; it becomes the monolith you left, minus a type checker across it.

## Testing a composed system

- **Each app tests itself in isolation**, against a mocked shell and the contract package.
- **Contract tests** check that a remote still exposes what the shell expects and that events match the published types. Module Federation's generated types turn many of these into compile errors.
- **A small end-to-end suite runs against the composed system** — the exact versions about to go live — on every deploy, covering only critical journeys: login, add to cart, pay.
- **Test the failure path:** block a remote's manifest and check that the error boundary renders something useful.

## A decision framework, and the modular monolith first

| Question | Leans monolith | Leans micro-frontends |
| --- | --- | --- |
| How many teams ship to this frontend? | One to three | Several, with separate roadmaps |
| Is the deploy pipeline the bottleneck? | No, or fixable with better CI | Yes, after investing in CI |
| Do teams need different release cadences? | Rarely | Often, and it blocks business |
| Are domain boundaries stable? | Still changing | Stable for a year or more |
| Is there someone to own the shell and the platform? | No | Yes |
| Is there a legacy app to migrate gradually? | No | Yes |

If most answers lean left, start with a **modular monolith**: one deployable app in a monorepo, split into packages by domain, with boundaries enforced by lint rules and code owners, and CI that only builds and tests what changed (see [monorepo lessons](/blog/monorepo-lessons-bun-turborepo) and [CI for a frontend monorepo](/blog/ci-for-frontend-monorepo)). You get clear ownership and most of the autonomy at a fraction of the cost, and well-separated packages are exactly what you'd extract later if you need independent deploys.

<Callout>
  The worst setup I've seen is micro-frontends with fuzzy boundaries: every feature touches three apps, so every release needs three coordinated deploys. That's a distributed monolith, and it's worse than either option.
</Callout>

## Key takeaways

<Checklist>

- Micro-frontends solve team coordination and deploy independence, not code quality or performance.
- Budget for the costs: duplicated dependencies, UX drift, extra requests, versioning and N pipelines.
- Prefer route-level composition when you can; use Module Federation when you need composition inside a page.
- Treat shared singletons (React, design system) as a platform contract and upgrade them together.
- Share the URL and a small typed event contract, not a global store; change contracts additively.
- Test apps in isolation, add contract tests, and run a small end-to-end suite on the composed versions.
- Start with a modular monolith; extract micro-frontends when the organization, not the code, demands it.

</Checklist>
