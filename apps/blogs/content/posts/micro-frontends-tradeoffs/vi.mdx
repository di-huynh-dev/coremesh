Sáu tháng sau, team nào cũng deploy độc lập được — nhưng bundle có ba bản của cùng một thư viện ngày tháng, hai kiểu button hơi lệch nhau, và một sự cố production do lệch phiên bản React giữa shell và một remote. ## Micro-frontends giải bài toán tổ chức

Micro-frontends chia frontend thành nhiều phần do các team khác nhau sở hữu và deploy, rồi ghép lại thành một sản phẩm. Bỏ lớp công cụ đi thì giá trị nằm ở **con người**:

- **Deploy độc lập.** Team A ship lúc 10 giờ sáng mà không phải chờ test chập chờn của team B.
- **Quyền sở hữu rõ ràng.** Một team nắm checkout từ đầu đến cuối: code, pipeline, on-call, metrics.
- **Migrate dần dần.** Có thể thay một ứng dụng legacy theo từng route (strangler pattern) thay vì viết lại một lần.

Hiệu năng và chất lượng code không có trong danh sách đó. Micro-frontends không làm code tốt lên; chúng làm **ranh giới** khó vượt qua hơn — có lợi khi ranh giới đúng, có hại khi sai.

Câu mình luôn tự hỏi: nỗi đau đến từ **phối hợp giữa các team**, hay từ chính code? Nếu ba kỹ sư đang giẫm chân nhau, bạn cần module tốt hơn, không phải deploy tách rời.

## Cái giá thật sự

| Chi phí | Thực tế trông như thế nào |
| --- | --- |
| Dependency bị nhân bản | Không chia sẻ thì mỗi app bundle một bản; chia sẻ thì sinh ràng buộc phiên bản |
| UX thiếu nhất quán | Spacing, loading, thông báo lỗi, focus khác nhau giữa các phần của một sản phẩm |
| Hiệu năng | Nhiều JavaScript hơn, nhiều request hơn, waterfall khi shell phải tải xong thì remote mới bắt đầu tải |
| State dùng chung | Auth, giỏ hàng, feature flag, ngôn ngữ: app nào cũng cần, không ai nên sở hữu store toàn cục |
| Phiên bản | Remote deploy thay đổi phá vỡ, shell trên production gãy dù không đổi dòng code nào |
| Vận hành | N pipeline, N môi trường preview, N bộ dashboard, và cách biết phiên bản nào đang chạy cùng nhau |

Dòng cuối hay bị đánh giá thấp. Với monolith, "cái gì đang chạy trên production" là một commit hash. Với micro-frontends, đó là một tổ hợp phiên bản **chưa ai test cùng nhau**, trừ khi bạn chủ động làm việc đó.

<Callout>
  Micro-frontends chuyển độ phức tạp từ codebase sang runtime và sang tổ chức. Nếu không có platform team (hoặc ít nhất một người) sở hữu shell, dependency dùng chung và hợp đồng giữa app, độ phức tạp đó rơi vào người đang trực on-call.
</Callout>

## Các cách tích hợp

Có năm cách chính để ghép app, khác nhau chủ yếu ở việc ghép **vào lúc nào**.

| Cách làm | Thời điểm ghép | Deploy độc lập | Mức cô lập | Rủi ro chính |
| --- | --- | --- | --- | --- |
| Package lúc build | Khi build host | Không (host phải build lại) | Không có | Chỉ là monorepo thêm vài bước |
| Module Federation | Runtime, trên trình duyệt | Có | Thấp (chung JS realm) | Phiên bản dependency dùng chung |
| Import maps + ES modules | Runtime, trên trình duyệt | Có | Thấp | Công cụ, hỗ trợ trình duyệt cho ca nâng cao |
| Iframe | Runtime, document riêng | Có | Mạnh | UX, accessibility, hiệu năng |
| Ghép phía server / theo route | Server hoặc edge | Có | Theo route hoặc fragment | Điều hướng giữa app và layout chung |

### Package lúc build

Mỗi team publish một package, host bundle tất cả. Đơn giản, có type, tự dedupe — nhưng mọi thay đổi vẫn cần host build và deploy lại, nên bạn mất đúng lý do chính để làm micro-frontends. Mình xem đây là một cách tổ chức monolith.

### Module Federation 2.0

Module Federation khởi đầu là tính năng của webpack 5. Bản 2.0, stable từ tháng 4/2026, tách runtime khỏi bundler và chạy với Rspack, webpack và bundler khác qua plugin. Nó bổ sung manifest (`mf-manifest.json`) mô tả những gì remote expose, type TypeScript sinh tự động cho remote, runtime plugin, và Chrome devtools cho thấy remote và phiên bản shared nào thực sự đã tải.

Một remote build bằng Rsbuild expose một trang và khai báo những gì nó chia sẻ. File `rsbuild.config.ts` của team checkout:

```ts
import { defineConfig } from "@rsbuild/core";
import { pluginReact } from "@rsbuild/plugin-react";
import { pluginModuleFederation } from "@module-federation/rsbuild-plugin";

export default defineConfig({
  plugins: [
    pluginReact(),
    pluginModuleFederation({
      name: "checkout",
      exposes: {
        "./CheckoutPage": "./src/CheckoutPage.tsx",
      },
      shared: {
        react: { singleton: true, requiredVersion: "^19.0.0" },
        "react-dom": { singleton: true, requiredVersion: "^19.0.0" },
        "@shop/design-system": { singleton: true, requiredVersion: "^4.0.0" },
      },
    }),
  ],
});
```

Shell dùng cùng plugin và khối `shared`, nhưng đăng ký remote lúc runtime từ endpoint cấu hình thay vì hardcode URL. Nhờ vậy có deploy độc lập và rollback tức thì: trỏ cấu hình về manifest trước là xong. `CheckoutUnavailable` và `PageSkeleton` bên dưới là các component bình thường nằm trong shell.

```tsx
import { lazy, Suspense, type ComponentType } from "react";
import { ErrorBoundary } from "react-error-boundary";
import { loadRemote, registerRemotes } from "@module-federation/enhanced/runtime";

type RemoteEntries = Record<string, string>;

export async function registerRemotesFromConfig() {
  const response = await fetch("/api/frontend-remotes");
  const entries: RemoteEntries = await response.json();
  registerRemotes(Object.entries(entries).map(([name, entry]) => ({ name, entry })));
}

const CheckoutPage = lazy(async () => {
  const remoteModule = await loadRemote<{ default: ComponentType }>("checkout/CheckoutPage");
  if (!remoteModule) throw new Error("checkout/CheckoutPage failed to load");
  return remoteModule;
});

export function CheckoutRoute() {
  return (
    <ErrorBoundary fallback={<CheckoutUnavailable />}>
      <Suspense fallback={<PageSkeleton />}>
        <CheckoutPage />
      </Suspense>
    </ErrorBoundary>
  );
}
```

Hai điều quan trọng hơn cấu hình. Thứ nhất, `singleton` không "đảm bảo một phiên bản": nếu lệch phiên bản, bản cao nhất thắng và bên kia chỉ nhận cảnh báo trong console. Team mình đã chạy một bản minor React mà một remote chưa từng test cùng, đúng theo cách đó. Hãy xem các singleton dùng chung là hợp đồng của cả platform và nâng cấp chúng cùng lúc. Thứ hai, mỗi remote là một dependency qua mạng: bọc nó trong error boundary với fallback có ích, đừng để trang trắng.

Một lưu ý riêng cho Next.js: team Module Federation đã thông báo end of life cho `nextjs-mf`, và plugin này chưa từng hỗ trợ App Router. Với Next.js 16, mình dùng cách ghép theo route (ở dưới).

### Import maps

ES modules gốc cộng import map cho phép ghép lúc runtime mà không cần runtime của federation. HTML của shell ánh xạ bare specifier sang URL, mỗi team cập nhật entry của mình:

```html
<script type="importmap">
  {
    "imports": {
      "react": "/shared/react-19.2.0.js",
      "react-dom/client": "/shared/react-dom-client-19.2.0.js",
      "@shop/checkout": "https://checkout.example.com/releases/412/entry.js"
    }
  }
</script>
<script type="module">
  import { mount } from "@shop/checkout";
  mount(document.getElementById("checkout-root"));
</script>
```

Một import map đơn lẻ chạy trên mọi trình duyệt hiện đại; nhiều import map cùng lúc thì Firefox vẫn chưa bật mặc định, nên mình sinh một map duy nhất ở server cho mỗi request. Điểm trừ: mọi thư viện dùng chung phải có bản build ES module chuẩn, và không có cơ chế thương lượng phiên bản như Module Federation.

### Iframe và ghép phía server

**Iframe** cho cô lập thật sự: JS realm và CSS riêng, crash cũng chỉ nằm bên trong. Hợp để nhúng công cụ bên thứ ba hoặc legacy. Với luồng sản phẩm cốt lõi thì khó: focus, kích thước, deep link, nút back và trình đọc màn hình đều cần thêm công, và mỗi frame tự tải framework riêng.

**Ghép phía server** chia theo route. Với multi-zones của Next.js, mỗi zone là một app Next.js bình thường có `assetPrefix` riêng, và app chính chuyển path sang zone bằng rewrites. Đây là cách mình khuyên dùng nhiều nhất, vì mỗi route vẫn có đủ SSR và React Server Components. File `next.config.ts` của app chính:

```ts
import type { NextConfig } from "next";

const checkoutOrigin = process.env.CHECKOUT_ORIGIN ?? "http://localhost:3002";

const nextConfig: NextConfig = {
  async rewrites() {
    return [
      { source: "/checkout", destination: `${checkoutOrigin}/checkout` },
      { source: "/checkout/:path+", destination: `${checkoutOrigin}/checkout/:path+` },
      { source: "/checkout-static/:path+", destination: `${checkoutOrigin}/checkout-static/:path+` },
    ];
  },
};

export default nextConfig;
```

Đánh đổi: điều hướng giữa các zone là tải lại toàn trang, nên link sang zone khác phải là thẻ `a` thường, không phải component `Link`, và Server Actions cần khai báo domain người dùng truy cập trong `serverActions.allowedOrigins`. Người dùng qua lại giữa các khu vực càng nhiều, hard navigation càng lộ rõ.

## Design system và quyền sở hữu routing

Cách hiệu quả nhất để giữ UX nhất quán là **một design system dùng chung do một team sở hữu**. Token dạng CSS variable (xem bài [design token và theming](/blog/design-tokens-and-theming)) là lớp an toàn nhất để chia sẻ vì không phụ thuộc framework và đổi được lúc runtime. Component thì khó hơn: làm singleton federated thì mọi app phải chạy được với phiên bản shell tải; mỗi app tự bundle thì sẽ lệch dần. Mình chọn singleton và coi việc nâng major là một đợt release có phối hợp.

Routing cũng cần luật rõ ràng không kém:

- **Shell sở hữu các route cấp cao nhất** và layout: header, điều hướng, cổng xác thực.
- Mỗi app sở hữu **mọi thứ dưới prefix của mình** (`/checkout/*`) cùng routing nội bộ.
- Điều hướng giữa các app đi qua URL, không bao giờ import router của app khác.

## Hợp đồng giữa các app

Các app càng ít chia sẻ càng tốt. URL là state dùng chung tốt nhất: serialize được, chia sẻ link được, không ai sở hữu. Với vài thứ các app thật sự phải báo cho nhau, mình publish một hợp đồng event nhỏ có type:

```ts
export type ShellEvents = {
  "cart:item-added": { sku: string; quantity: number };
  "auth:session-changed": { userId: string | null };
};

export function emitShellEvent<K extends keyof ShellEvents>(type: K, detail: ShellEvents[K]) {
  window.dispatchEvent(new CustomEvent(type, { detail }));
}

export function onShellEvent<K extends keyof ShellEvents>(
  type: K,
  handler: (detail: ShellEvents[K]) => void,
): () => void {
  const listener = (event: Event) => handler((event as CustomEvent<ShellEvents[K]>).detail);
  window.addEventListener(type, listener);
  return () => window.removeEventListener(type, listener);
}
```

Luật quan trọng hơn code: payload **chỉ được thêm, không được bớt**, thay đổi phá vỡ thì dùng tên event mới, và auth nằm ở shell — app hỏi shell, không đọc storage của nhau. Tránh store toàn cục dùng chung; nó sẽ thành chính cái monolith bạn vừa rời, chỉ thiếu type checker bao trùm.

## Test một hệ thống được ghép lại

- **Mỗi app tự test độc lập**, với shell giả lập và package hợp đồng.
- **Contract test** kiểm tra remote vẫn expose đúng thứ shell cần và event khớp với type đã publish. Type sinh tự động của Module Federation biến nhiều lỗi kiểu này thành lỗi biên dịch.
- **Một bộ end-to-end nhỏ chạy trên hệ thống đã ghép** — đúng tổ hợp phiên bản sắp lên production — ở mỗi lần deploy, chỉ phủ hành trình quan trọng: đăng nhập, thêm vào giỏ, thanh toán.
- **Test cả nhánh lỗi:** chặn manifest của một remote và kiểm tra error boundary hiển thị thứ có ích.

## Khung ra quyết định, và modular monolith trước

| Câu hỏi | Nghiêng về monolith | Nghiêng về micro-frontends |
| --- | --- | --- |
| Bao nhiêu team ship vào frontend này? | Một đến ba | Nhiều, với roadmap riêng |
| Pipeline deploy có phải nút thắt? | Không, hoặc sửa được bằng CI tốt hơn | Có, sau khi đã đầu tư cho CI |
| Các team có cần nhịp release khác nhau? | Hiếm khi | Thường xuyên, và nó chặn việc kinh doanh |
| Ranh giới domain đã ổn định chưa? | Vẫn đang thay đổi | Ổn định từ một năm trở lên |
| Có ai sở hữu shell và platform không? | Không | Có |
| Có ứng dụng legacy cần migrate dần? | Không | Có |

Nếu phần lớn câu trả lời nghiêng về bên trái, hãy bắt đầu với **modular monolith**: một ứng dụng deploy duy nhất trong monorepo, chia package theo domain, ranh giới được ép bằng lint rule và code owner, CI chỉ build và test những gì thay đổi (xem [bài học monorepo](/blog/monorepo-lessons-bun-turborepo) và [CI cho frontend monorepo](/blog/ci-for-frontend-monorepo)). Bạn có quyền sở hữu rõ ràng và phần lớn sự tự chủ với chi phí thấp hơn nhiều, và các package tách tốt chính là thứ bạn sẽ tách ra sau nếu thật sự cần deploy độc lập.

<Callout>
  Setup tệ nhất mình từng thấy là micro-frontends với ranh giới mập mờ: tính năng nào cũng chạm vào ba app, nên bản release nào cũng cần ba lần deploy phối hợp. Đó là một distributed monolith, và nó tệ hơn cả hai lựa chọn kia.
</Callout>

## Tóm tắt

<Checklist>

- Micro-frontends giải bài toán phối hợp giữa các team và deploy độc lập, không phải chất lượng code hay hiệu năng.
- Tính trước các chi phí: dependency nhân bản, UX lệch nhau, thêm request, quản lý phiên bản và N pipeline.
- Ưu tiên ghép theo route khi có thể; dùng Module Federation khi cần ghép bên trong một trang.
- Coi các singleton dùng chung (React, design system) là hợp đồng của platform và nâng cấp cùng lúc.
- Chia sẻ URL và một hợp đồng event nhỏ có type, không chia sẻ store toàn cục; chỉ thay đổi hợp đồng theo kiểu bổ sung.
- Test từng app độc lập, thêm contract test, và chạy một bộ end-to-end nhỏ trên tổ hợp phiên bản đã ghép.
- Bắt đầu với modular monolith; chỉ tách micro-frontends khi tổ chức, chứ không phải code, đòi hỏi điều đó.

</Checklist>
